# 音素アライメント評価

## 1. 目的

Phase 1では、既知の発話テキストと録音音声から、日本語の5母音に対応する時間区間を抽出する。

複数の既存アライメント方式を同じ条件で比較し、後続フェーズで話者認証用データセットを構築するための基準方式を選定する。

作業の進捗、試行錯誤、エラー、途中結果は [GitHub Issue #1](https://github.com/muzin00/phonia/issues/1) で管理する。本書には、確定した設計判断と最終的な検証結果のみを反映する。

```text
入力音声 + 発話テキスト
          ↓
音素アライメント
          ↓
音素ラベル + 開始時刻 + 終了時刻
          ↓
元音声から母音区間を抽出
```

## 2. 検証対象

対象音素は日本語の5母音とする。

```text
/a/ /i/ /u/ /e/ /o/
```

アライメントには既存モデルを利用し、本フェーズでは新しい音響モデルを学習しない。

## 3. 比較する方式

### A. Montreal Forced Aligner

日本語の学習済み音響モデル、発音辞書、G2Pを利用するforced alignment方式。

- 実装: Montreal Forced Aligner
- 音響モデル: `japanese_mfa`
- 役割: 基準となるforced alignment方式
- 実行環境: CPU
- 主な出力: 音素ごとの開始時刻と終了時刻

参照:

- [Montreal Forced Aligner](https://github.com/MontrealCorpusTools/Montreal-Forced-Aligner)
- [Japanese MFA acoustic model](https://mfa-models.readthedocs.io/en/latest/acoustic/Japanese/Japanese%20MFA%20acoustic%20model%20v3_0_0.html)

### B. Julius Speech Segmentation Toolkit

Juliusの音素単位forced alignmentを利用する日本語向け方式。

- 実装: Julius Speech Segmentation Toolkit
- 初期設定: 付属monophoneモデル
- 役割: 日本語向けの軽量な比較方式
- 実行環境: CPU
- 主な出力: 音素ごとの開始時刻、終了時刻、音響尤度

triphoneモデルは、標準のmonophoneモデルで必要な品質を得られない場合の追加設定として扱い、独立した第四の方式には数えない。

参照:

- [Julius](https://github.com/julius-speech/julius)
- [Speech Segmentation Toolkit](https://github.com/julius-speech/segmentation-kit)

### C. Wav2Vec2 phoneme CTC ONNX

多言語phoneme CTCモデルをONNX Runtimeで実行し、期待音素列とのCTC forced alignmentを行う方式。

- ベースモデル: `facebook/wav2vec2-xlsr-53-espeak-cv-ft`
- 実行形式: ONNX
- 推論ランタイム: ONNX Runtime
- 役割: ニューラルモデルかつポータブルな比較方式
- 主な出力: フレームごとの音素logitsから算出した開始時刻と終了時刻

公式モデルのリビジョンを固定してONNXへ変換する。第三者が公開する変換済みモデルは技術検証には利用できるが、正式な比較では変換手順と出力の同等性を管理する。

初期比較では量子化による境界変化を避けるため、FP32モデルを利用する。INT8などの量子化はPhase 1の比較対象外とする。

参照:

- [Wav2Vec2 XLSR phoneme model](https://huggingface.co/facebook/wav2vec2-xlsr-53-espeak-cv-ft)

## 4. 共通処理フロー

```text
元音声
  ↓
共通の音声検証・前処理
  ↓
各アライナーが要求する入力へ変換
  ↓
音素アライメント
  ↓
モデル固有の結果を保存
  ↓
共通形式へ変換
  ↓
5母音を元音声から抽出
```

比較前の音声処理条件は統一する。モデルごとに異なる条件が必要な場合も、同一の元音声から派生データを生成し、その変換条件を記録する。

元音声は変更せず保存し、音素区間の切り出しは常に元音声と時間情報から再生成できるようにする。

## 5. 公平な比較

G2Pの違いと音響アライメントの違いを混同しないよう、評価を二段階に分ける。

### 5.1 アライナー単体評価

人手で確認した共通の期待音素列を、各方式の音素体系へ変換して与える。

```text
共通の期待音素列
  ├── MFA用音素列
  ├── Julius用音素列
  └── eSpeak用音素列
```

この評価では、テキスト解析や辞書検索の違いを除外し、音響モデルとアライメント処理による境界の差を比較する。

### 5.2 エンドツーエンド評価

通常の日本語テキストから各方式のG2P・辞書処理を通してアライメントする。

この評価には以下の影響を含める。

- 漢字や読みの変換
- 辞書外語
- 発音の揺れ
- 長音、促音、撥音
- 無声化母音

## 6. 評価データ

最初の評価セットは30〜50発話程度とし、少なくとも以下を含める。

- 5母音が十分に出現する発話
- 複数の話者
- 異なる声質
- 文頭、文中、文末の母音
- 短母音と長母音
- `/i/` と `/u/` の無声化候補
- 異なる発話速度
- 可能であれば異なる収録セッション

比較の基準として、対象母音の開始時刻と終了時刻を人手で確認する。境界が曖昧な区間はその事実を記録し、明確な正解として扱わない。

## 7. 評価指標

### 7.1 境界誤差

人手で確認した境界との差をミリ秒単位で測定する。

```text
start_error = 自動抽出した開始時刻 - 基準開始時刻
end_error   = 自動抽出した終了時刻 - 基準終了時刻
```

以下を集計する。

- 開始境界の絶対誤差
- 終了境界の絶対誤差
- 中央値
- 90パーセンタイル
- 許容範囲内に収まる割合

許容範囲は、`10ms`、`20ms`、`30ms`、`50ms`の各段階で確認する。

### 7.2 区間品質

- 基準区間との重なり率
- 抽出区間の長さ
- 極端に短い区間の割合
- 無音のみ、またはほぼ無音となった区間の割合
- 対象母音を取得できた割合
- 音素別の成功率

### 7.3 処理品質

- アライメント失敗率
- G2Pまたは辞書処理の失敗率
- 1音声あたりの処理時間
- 最大メモリ使用量
- Apple Silicon環境での安定性
- セットアップと再実行の容易さ

各方式が出力するスコアや尤度は定義と尺度が異なるため、方式間で数値を直接比較しない。それぞれの方式内で失敗検出や品質判定に利用できるかを確認する。

## 8. 音素表記の正規化

各方式の生の音素ラベルを失わずに保存し、プロジェクト内の共通表記へ変換する。

```text
raw_phoneme        モデルが出力した音素
normalized_phoneme プロジェクト内の共通音素
```

5母音への正規化では、長音や無声化などの情報を別属性として保持する。

```json
{
  "raw_phoneme": "ɯ̥",
  "normalized_phoneme": "u",
  "is_long": false,
  "is_devoiced": true
}
```

正規化規則は設定またはバージョン管理されたマッピングとして保持し、結果から使用した規則を追跡できるようにする。

## 9. 共通出力

各アライナーの結果は、最低限、次の情報を持つ共通形式へ変換する。

```json
{
  "utterance_id": "sample_001",
  "speaker_id": "speaker_001",
  "session_id": "session_001",
  "source_file": "...",
  "transcript": "...",
  "aligner": "mfa",
  "model_id": "japanese_mfa",
  "model_version": "...",
  "raw_phoneme": "a",
  "normalized_phoneme": "a",
  "start_sec": 0.42,
  "end_sec": 0.56,
  "duration_sec": 0.14,
  "score": null,
  "score_kind": null,
  "is_long": false,
  "is_devoiced": false
}
```

具体的なスキーマ、必須項目、ファイル配置は実装開始前に確定する。

## 10. 実装境界

モデル固有処理は共通インターフェースの背後へ分離する。

```text
PhonemeAligner
  ├── MFAAligner
  ├── JuliusAligner
  └── OnnxCtcAligner
```

共通処理は、特定のアライナーへ依存させない。

- 入力の検証
- 音声前処理
- 共通形式への変換
- 音素表記の正規化
- 元波形からの区間抽出
- 評価指標の計算
- 結果レポートの生成

## 11. 比較結果の扱い

初期段階では複数方式の結果を平均したり、境界を合成したりしない。方式ごとの結果を独立して保存し、差を観察する。

Phase 1では人手境界との比較を行うが、最終的な採用判断には後続フェーズの話者認証性能も含める。

```text
MFAで抽出したデータ     → 共通encoder → 認証性能
Juliusで抽出したデータ  → 共通encoder → 認証性能
ONNXで抽出したデータ    → 共通encoder → 認証性能
```

境界誤差が最小の方式が、話者情報を最も保持するとは限らないためである。

## 12. Phase 1の成果物

- 3方式を実行するアライナー
- 共通の入力検証と音声前処理
- モデル固有出力と共通形式の変換処理
- 5母音の波形区間抽出処理
- 音素表記の正規化規則
- 人手で確認した小規模評価セット
- 境界精度、成功率、実行性能の比較レポート
- 後続フェーズで使用する基準方式の選定結果

## 13. 完了条件

次の条件を満たした時点でPhase 1を完了とする。

- 3方式を同じ評価音声に対して実行できる。
- 各方式のモデルと設定バージョンが固定されている。
- 元音声から抽出結果までの由来を追跡できる。
- 人手境界を基準とした比較結果が作成されている。
- 音素別の失敗傾向が整理されている。
- Apple Silicon上での実行時間と安定性が確認されている。
- 後続フェーズで使用する方式を、結果に基づいて選定できる。

すべての方式が必要な品質を満たさない場合は、無理に一つを採用せず、モデルの適応、別モデル、または抽出方針の変更を検討する。

## 14. Phase 1の対象外

- 音素話者encoderの学習
- ユーザー登録用プロファイルの作成
- 本人照合スコアの算出
- 認証閾値の決定
- オンラインでのプロファイル更新
- リプレイや生成音声の検出
- リアルタイム処理の最適化
- ONNXモデルの量子化比較
