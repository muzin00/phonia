# 音素アライメント評価

## 1. 目的

Phase 1では、既知の発話テキストと録音音声から、日本語の5母音に対応する、後続処理で利用可能な波形区間を抽出する。

複数の既存アライメント方式を同じ条件で比較し、期待する母音を欠落なく取得でき、別の母音の核を含まず、後続処理で利用できる区間を得られる基準方式を選定する。音声学的に厳密な境界時刻や、前後音素の影響を完全に除いた母音定常部の推定自体を目的にはしない。

作業の進捗、試行錯誤、エラー、途中結果は [GitHub Issue #1](https://github.com/muzin00/phonia/issues/1) で管理する。本書には、確定した設計判断と最終的な検証結果のみを反映する。

```text
入力音声 + 発話テキスト
          ↓
G2Pと読みの確認
          ↓
3方式による音素アライメント
          ↓
音素正規化と母音区間抽出
          ↓
機械検査 + 対象を絞った支援レビュー
          ↓
後続処理で利用可能な方式を選定
```

## 2. 検証対象

対象音素は日本語の5母音とする。

```text
/a/ /i/ /u/ /e/ /o/
```

アライメントには既存モデルを利用し、本フェーズでは新しい音響モデルを学習しない。

### 2.1 母音区間の定義

本評価における母音区間は、対象母音の音響的な実現を含み、別の母音の核を含まない連続した波形区間とする。

- 対象母音を後続処理へ利用できる程度に含む。
- 異なる母音の核を同じ区間へ含めない。
- 前後の子音との遷移や共調音が境界付近に残ることは許容する。
- 子音らしい成分が聞こえることだけを理由に不適切とはしない。
- 音声学的に純粋な母音定常部や、専門家が定めた正解境界を意味しない。

アライナーが出力した一つの母音phone区間を原子単位とする。同じ母音が直接隣接しても結合せず、語境界をまたぐ結合も行わない。たとえば「明王」や「も多い」に連続する /o/ があっても、アライナーが複数区間として出力した場合はそれぞれを保持する。一方、アライナー自身が長母音`oː`を一つのphone区間として出力した場合は、人為的な内部境界を追加せず一つの区間として保持する。先行子音全体を意図的に含めるモーラ区間とは区別する。

方式間比較などで複数区間をまとめる必要がある場合は、元区間のIDを参照する派生的な比較単位として別に生成する。結合した比較単位をアライナーの出力区間やニューラルネットワークの学習区間として扱わない。

各アライナーの生の音素境界は失わずに保存する。必要になった場合は子音と母音からモーラ区間を再構成できるが、Phase 1ではモーラ区間の生成や認証利用を必須成果物にしない。

## 3. 比較する方式

### A. Montreal Forced Aligner

日本語の学習済み音響モデル、発音辞書、G2Pを利用するforced alignment方式。

- 実装: Montreal Forced Aligner
- 実装バージョン: `3.4.2`
- 音響モデル: `japanese_mfa`
- 音響モデルバージョン: `3.0.0`
- 発音辞書: `japanese_mfa` `3.0.0`
- 役割: 基準となるforced alignment方式
- 実行環境: CPU
- 主な出力: 音素ごとの開始時刻と終了時刻

参照:

- [Montreal Forced Aligner](https://github.com/MontrealCorpusTools/Montreal-Forced-Aligner)
- [Japanese MFA acoustic model](https://mfa-models.readthedocs.io/en/latest/acoustic/Japanese/Japanese%20MFA%20acoustic%20model%20v3_0_0.html)
- [Apple Silicon環境構築](aligners/mfa/README.md)

### B. Julius Speech Segmentation Toolkit

Juliusの音素単位forced alignmentを利用する日本語向け方式。

- 実装: Julius Speech Segmentation Toolkit
- 実装バージョン: `4.6`
- 実装コミット: `3b7174d0d4091f5e6ebb917769822032d079996f`
- 初期設定: 付属monophoneモデル
- segmentation-kitコミット: `e0e8bbaf98e27d19dfc6fe8312be607ad03592ad`
- 役割: 日本語向けの軽量な比較方式
- 実行環境: CPU
- 主な出力: 音素ごとの開始時刻、終了時刻、音響尤度

triphoneモデルは、標準のmonophoneモデルで必要な品質を得られない場合の追加設定として扱い、独立した第四の方式には数えない。

参照:

- [Julius](https://github.com/julius-speech/julius)
- [Speech Segmentation Toolkit](https://github.com/julius-speech/segmentation-kit)
- [Apple Silicon環境構築](aligners/julius/README.md)

パイロット3発話では、各発話80音素区間（文頭・文末無音を含む）を生成し、入力音素列との一致を確認した。各発話46母音区間、合計138区間を抽出し、期待母音列との不一致、時間範囲の異常、30 ms未満の区間、無音・低レベル区間は検出されなかった。3発話のアライメント処理時間はApple Silicon CPU上で合計約0.11秒だった。

MFAの合計108母音区間に対してJuliusが138区間となるのは、主にMFAが一つの長母音phoneとして出力する箇所を、Juliusには共通期待列どおり連続する個別母音として与えているためである。区間数を抽出成功率として直接比較せず、期待母音単位へ展開した列と原子区間の表現を区別する。

### C. Wav2Vec2 phoneme CTC ONNX

多言語phoneme CTCモデルをONNX Runtimeで実行し、期待音素列とのCTC forced alignmentを行う方式。

- ベースモデル: `facebook/wav2vec2-xlsr-53-espeak-cv-ft`
- モデルリビジョン: `2c733782da5604684829819a5eb744c193fe9398`
- 実行形式: ONNX
- 推論ランタイム: ONNX Runtime `1.30.0`
- 役割: ニューラルモデルかつポータブルな比較方式
- 主な出力: フレームごとの音素logitsから算出した開始時刻と終了時刻

公式モデルのリビジョンを固定してONNXへ変換する。第三者が公開する変換済みモデルは技術検証には利用できるが、正式な比較では変換手順と出力の同等性を管理する。

初期比較では量子化による境界変化を避けるため、FP32モデルを利用する。INT8などの量子化はPhase 1の比較対象外とする。

参照:

- [Wav2Vec2 XLSR phoneme model](https://huggingface.co/facebook/wav2vec2-xlsr-53-espeak-cv-ft)
- [Apple Silicon環境構築](aligners/wav2vec2/README.md)

公式PyTorchモデルをFP32 ONNXへ変換し、パイロット音声1件で全430フレームの
argmax出力が一致することを確認した。共通期待音素列をモデルのeSpeak IPA語彙へ
写像し、CTCの最尤経路から各音素の境界を復元した。

パイロット3発話では合計138母音区間を生成でき、期待列との構造不一致、30 ms
未満の区間、無音・低レベル区間は検出されなかった。一方、制約なし推論の期待
トークン列に対する編集誤り率は40.4%だった。

Juliusの同じ138原子母音区間と比較した結果、区間IoU中央値は0.566、重なりなし
は12件、いずれかの境界差が100 msを超えた区間は23件だった。重なりなし12件の
うち11件は、Juliusの人間レビューで利用可能と判定された区間である。モデル読込と
音声前処理を除く処理時間は3発話で約1.48秒で、Juliusの0.111秒に対して約13.3倍
だった。Wav2Vec2に有利な計測範囲でもJuliusより低速だった。

機械指標だけを見るとJuliusより不利だったが、少数区間を実際に聴いた参考確認では
明らかな品質不足は感じられず、聴感上はMFAと同程度という印象だった。方式間の
境界不一致と制約なし認識の誤り率は、forced alignment後の母音区間が利用不能で
あることを直接意味しない。

Wav2Vec2の全138件を対象とする定量的な人間レビューは実施しない。参考確認では
MFAと同程度、処理速度はMFAより大幅に速い一方、すでに全件レビューで良好だった
Juliusより約13.3倍遅く、Juliusを上回る根拠は得られなかった。このためPhase 1の
基準方式にはJuliusを採用する。

### 3.1 パイロットの母音別傾向

3発話の全件レビューを母音別に再集計した結果を以下に示す。採用率は各方式が出力した
原子区間を分母とする。MFAは長母音を一つの区間として保持するため、とくに `/o/` と
`/u/` ではJuliusと分母が異なり、方式間の率だけを精度差として扱わない。

| 母音 | MFA 採用 | Julius 採用 | MFA 非母音成分なし | Julius 非母音成分なし |
| --- | ---: | ---: | ---: | ---: |
| `/a/` | 15/21 (71.4%) | 13/21 (61.9%) | 4/21 (19.0%) | 5/21 (23.8%) |
| `/i/` | 12/18 (66.7%) | 13/18 (72.2%) | 8/18 (44.4%) | 9/18 (50.0%) |
| `/u/` | 11/12 (91.7%) | 13/15 (86.7%) | 3/12 (25.0%) | 9/15 (60.0%) |
| `/e/` | 5/6 (83.3%) | 6/6 (100.0%) | 3/6 (50.0%) | 3/6 (50.0%) |
| `/o/` | 36/51 (70.6%) | 58/78 (74.4%) | 18/51 (35.3%) | 42/78 (53.8%) |

- `/i/` は無声化候補を含み、聞き取りと境界の不確実判定が他母音より目立った。
- `/o/` は長母音と連続母音が多く、MFAとJuliusの表現粒度の差が最も大きかった。
  MFA対Juliusで境界差が100 msを超えた8区間も、すべて `/o/` だった。
- Juliusは `/u/` と `/o/` で、非母音成分を含まないと判定された割合がMFAより高かった。
- `/e/` は6件しかなく、100%という採用率から一般化はできない。全母音とも3発話の
  パイロット結果であり、30〜50発話への拡張結果を最終値とする。

集計値は [`data/evaluation-summary.json`](data/evaluation-summary.json) に保存し、
`uv run python scripts/summarize_alignment_evaluation.py` で元のアライメント・区間・
レビュー記録から再生成できる。Wav2Vec2は全件定量レビューを実施していないため、
母音別の人間採用率は算出しない。

## 4. 共通処理フロー

```text
元音声
  ↓
共通の音声検証・前処理
  ↓
各アライナーが要求する入力へ変換
  ↓
音素アライメント
  ↓
モデル固有の結果を保存
  ↓
共通形式へ変換
  ↓
各母音phone区間を共通表記へ正規化
  ↓
5母音を元音声から抽出
  ↓
構造・信号・方式間一致度を自動検査
  ↓
要確認区間と抜き取り区間を支援レビュー
```

比較前の音声処理条件は統一する。モデルごとに異なる条件が必要な場合も、同一の元音声から派生データを生成し、その変換条件を記録する。

元音声は変更せず保存し、音素区間の切り出しは常に元音声と時間情報から再生成できるようにする。

## 5. 公平な比較

G2Pの違いと音響アライメントの違いを混同しないよう、評価を二段階に分ける。

### 5.1 アライナー単体評価

G2Pで生成し、読みだけを人間が確認した共通の期待音素列を、各方式の音素体系へ変換して与える。

```text
共通の期待音素列
  ├── MFA用音素列
  ├── Julius用音素列
  └── eSpeak用音素列
```

この評価では、テキスト解析や辞書検索の違いを除外し、音響モデルとアライメント処理による境界の差を比較する。

### 5.2 エンドツーエンド評価

通常の日本語テキストから各方式のG2P・辞書処理を通してアライメントする。

この評価には以下の影響を含める。

- 漢字や読みの変換
- 辞書外語
- 発音の揺れ
- 長音、促音、撥音
- 無声化母音

## 6. 評価データ

最初の評価セットは30〜50発話程度とし、少なくとも以下を含める。

- 5母音が十分に出現する発話
- 複数の話者
- 異なる声質
- 文頭、文中、文末の母音
- 短母音と長母音
- `/i/` と `/u/` の無声化候補
- 異なる発話速度
- 可能であれば異なる収録セッション

評価は機械的な構造検査、音声信号の健全性検査、3方式の境界一致度を中心とする。不一致や異常を検出した区間と無作為抽出した区間だけを、事前に候補境界をマークした画面で人間が確認する。

非専門家による確認結果は精密な正解境界とは扱わない。専門家による参照境界が必要になった場合は、問題区間を絞って追加作成する。詳細は[半自動母音区間評価ガイドライン](annotation-guideline.md)と[母音区間支援レビューUI仕様](review-ui-spec.md)を参照する。

### 6.1 40発話への拡張結果

パイロットと同じ機械評価を、JVS由来の40発話、4話者、合計224.04秒へ拡張した。
各話者について取得元でWAVとラベルがそろう先頭10件を機械的に採用し、人手による
データ選別や信頼度付与は行っていない。再現手順と利用上の注意は
[`data/expansion/README.md`](data/expansion/README.md)に記載した。

| 項目 | MFA | Julius | Wav2Vec2 |
| --- | ---: | ---: | ---: |
| 処理できた発話 | 40/40 | 40/40 | 40/40 |
| 共通期待列と一致した発話 | 12/40 | 40/40 | 40/40 |
| 抽出した母音区間 | 998 | 1,164 | 1,164 |
| 自動品質フラグ | 2 | 22 | 11 |
| 計測時間 | 88.693秒 | 1.008秒 | 11.960秒 |
| 1発話あたり | 2,217.3 ms | 25.2 ms | 299.0 ms |

期待母音1,164単位の内訳は `/a/` 309、`/i/` 218、`/u/` 203、`/e/` 138、
`/o/` 296だった。JuliusとWav2Vec2は共通期待列をforced alignmentへ直接与えるため
全発話で列が一致した。MFAは日本語テキストから自身の辞書・G2Pを通す現行経路のため、
「風」の「ふう／かぜ」のような読みの差を28発話で検出した。これはアライメント失敗
ではなくエンドツーエンドのG2P不一致であり、MFA対Juliusの境界比較は列が一致した
12発話・286区間だけを対象にした。この範囲では重なりなしは0件、100 ms超の境界差は
`/o/` の6件だった。

Wav2Vec2対Juliusは全1,164区間を比較できた。母音別IoU中央値は `/a/` 0.622、
`/i/` 0.576、`/u/` 0.474、`/e/` 0.697、`/o/` 0.622で、重なりなしは40件、
100 ms超の境界差は86件だった。制約なし推論の期待トークン列に対する編集誤り率は
41.2%で、3発話パイロットの40.4%と同程度だった。

自動品質フラグはレビュー対象候補であり、そのまま抽出失敗件数とはみなさない。
Juliusの22件はすべて低レベル区間で、無声化母音を含む可能性がある。Wav2Vec2は
低レベル8件と30 ms未満3件、MFAは低レベル2件だった。40発話への拡張でも、速度、
共通期待列の安定した処理、Wav2Vec2との境界一致度を総合すると、Phase 1の基準方式を
Juliusとする判断は変わらない。

完全な機械可読結果は
[`data/expansion/evaluation-summary.json`](data/expansion/evaluation-summary.json)に保存し、
`uv run python scripts/summarize_expansion_evaluation.py`で再生成できる。Wav2Vec2の
計測時間はモデル読込と音声前処理を除くため、Juliusに有利な条件へ補正した速度比較
ではない。それでもJuliusは約11.9倍高速だった。

## 7. 評価指標

### 7.1 境界一致度

同じ期待母音に対応する方式間の境界差をミリ秒単位で測定する。

```text
start_delta(A, B) = abs(A.start_sec - B.start_sec)
end_delta(A, B)   = abs(A.end_sec - B.end_sec)
```

以下を集計する。

- 開始境界の方式間差
- 終了境界の方式間差
- 中央値
- 90パーセンタイル
- 許容範囲内に収まる割合

許容範囲は、`10ms`、`20ms`、`30ms`、`50ms`の各段階で確認する。

3方式の一致は正確さを保証しないため、専門家による参照境界がない限り境界精度とは呼ばない。

### 7.2 区間品質

- 方式間の区間重なり率
- 抽出区間の長さ
- 極端に短い区間の割合
- 無音のみ、またはほぼ無音となった区間の割合
- 対象母音を取得できた割合
- 音素別の成功率
- 支援レビューで対象母音を聞き取れた割合
- 別の母音を含むと判定された割合
- 子音などの許容可能な非母音成分が聞こえる割合

### 7.3 処理品質

- アライメント失敗率
- G2Pまたは辞書処理の失敗率
- 1音声あたりの処理時間
- 最大メモリ使用量
- Apple Silicon環境での安定性
- セットアップと再実行の容易さ

各方式が出力するスコアや尤度は定義と尺度が異なるため、方式間で数値を直接比較しない。それぞれの方式内で失敗検出や品質判定に利用できるかを確認する。

## 8. 音素表記の正規化

各方式の生の音素ラベルを失わずに保存し、プロジェクト内の共通表記へ変換する。

```text
raw_phoneme        モデルが出力した音素
normalized_phoneme プロジェクト内の共通音素
```

5母音への正規化では、長音や無声化などの情報を別属性として保持する。

```json
{
  "raw_phoneme": "ɯ̥",
  "normalized_phoneme": "u",
  "is_long": false,
  "is_devoiced": true
}
```

正規化規則は設定またはバージョン管理されたマッピングとして保持し、結果から使用した規則を追跡できるようにする。

同じ母音が連続する場合も、モデルが出力した各phone区間を`vowel_interval`として個別に保持する。ラベルは5母音へ正規化するが、時間境界は結合・平均・補間しない。語境界の有無にかかわらず、後処理による時間結合は禁止する。

```text
MFA出力: oː(3.410–3.620), oː(3.620–3.680)
   ↓ 正規化（結合しない）
vowel_interval 1: o, 3.410–3.620, expected_units: 2
vowel_interval 2: o, 3.620–3.680, expected_units: 2
```

`expected_units`は長母音表現を期待母音列へ展開して照合するための属性であり、区間を分割または結合する指示ではない。たとえば一つの`oː`区間は`expected_units: 2`のまま一つの学習・レビュー区間になる。方式間比較のために連続区間をまとめる場合は、元の`vowel_interval_id`一覧を持つ派生的な比較単位を作り、学習データには使用しない。

## 9. 共通出力

各アライナーの結果は、最低限、次の情報を持つ共通形式へ変換する。

```json
{
  "utterance_id": "sample_001",
  "speaker_id": "speaker_001",
  "session_id": "session_001",
  "source_file": "...",
  "transcript": "...",
  "aligner": "mfa",
  "aligner_version": "3.4.2",
  "model_id": "japanese_mfa",
  "model_version": "3.0.0",
  "raw_phonemes": ["a"],
  "raw_intervals": [
    {"phoneme": "a", "start_sec": 0.42, "end_sec": 0.56}
  ],
  "normalized_phoneme": "a",
  "start_sec": 0.42,
  "end_sec": 0.56,
  "duration_sec": 0.14,
  "score": null,
  "score_kind": null,
  "is_long": false,
  "is_devoiced": false,
  "vowel_interval_id": "sample_001-mfa-vowel-000",
  "expected_units": 1

```

具体的なスキーマ、必須項目、ファイル配置は実装開始前に確定する。

`start_sec`と`end_sec`は各アライナーが推定した母音境界であり、前後音素の音響的影響が完全に消える時刻を保証しない。母音区間としての品質は、対象母音の利用可能性と別の母音核の有無を支援レビューで評価する。この評価は方式全体の性能集計に使用し、個別区間の学習データ選別には使用しない。

## 10. 実装境界

モデル固有処理は共通インターフェースの背後へ分離する。

```text
PhonemeAligner
  ├── MFAAligner
  ├── JuliusAligner
  └── OnnxCtcAligner
```

共通処理は、特定のアライナーへ依存させない。

- 入力の検証
- 音声前処理
- 共通形式への変換
- 音素表記の正規化
- 元波形からの区間抽出
- 評価指標の計算
- レビュー対象の自動振り分け
- 支援レビュー画面と回答の保存
- 結果レポートの生成

## 11. 比較結果の扱い

初期段階では複数方式の結果を平均したり、境界を合成したりしない。方式ごとの結果を独立して保存し、差を観察する。

Phase 1では自動検査、方式間の一致度、対象を絞った支援レビューで比較する。最終的な採用判断には後続フェーズの話者認証性能も含める。

```text
MFAで抽出したデータ     → 共通encoder → 認証性能
Juliusで抽出したデータ  → 共通encoder → 認証性能
ONNXで抽出したデータ    → 共通encoder → 認証性能
```

方式間の境界差が小さい方式や、専門家による境界に近い方式が、話者情報を最も保持するとは限らないためである。

### 11.1 後続PoCへ渡す区間

支援レビューは方式ごとの抽出成功率と失敗傾向を評価するために使用し、個別区間の選別や境界修正には使用しない。後続の学習PoCでは、採用したアライナーが出力した区間を、機械的に学習入力を構成できる限りそのまま使用する。

区間ごとの信頼度推定、レビュー結果に基づく除外、品質による重み付け、高品質区間だけのサブセット作成は行わない。区間が生成されない、時刻が不正、音声を読み出せないなどの処理不能例は学習入力にできないため使用対象外とするが、アライナーの失敗として集計へ含める。

レビュー回答や品質フラグは分析用の属性として保持できるが、初期PoCでは学習データの採否や重みを変えない。これにより、後続の認証性能には採用方式が生成する区間品質も含まれる。
